# ADR-004: bounded development profile persistence

Status: accepted for P02.04 non-secret development profiles and bounded P02.05 copied-input projection/journal, 2026-10-28. Full historical migration, shell adoption and credential policy remain open.

2026-10-29 continuation: accepted single-owner active durable repository below; production shell/worker composition remains open.

## Evidence and decision

Feishin `7d6ad318c79802e226996cfc39acba6b05bb22e8` persists credential-bearing authentication state (`auth.store.ts:25-118`) and split settings (`store/utils.ts:178-325`). The settings defaults include `language: 'en'` and `followSystemTheme: false` (`settings.store.ts:1374,1360`). Current Rust shells have no durable application state. We need independent development persistence before authentication or queue integration, without reading the Electron profile.

Use one small `feishin-storage` crate beside the dependency-free domain crate. Versioned storage DTOs are distinct from domain values; persisted profile IDs are strings validated for bounded nonempty uniqueness, and backend kind is a closed schema enum. Future application composition converts them to domain ServerId/ServerType. Schema v1 contains at most 64 non-secret server descriptors (ID, name, HTTP(S) endpoint, backend), an optional selected server ID and two preferences. It intentionally does not persist the complete domain ServerProfile or settings surface. No credentials, runtime handles, queue or cache belong to this schema.

The native blocking adapter takes an explicit absolute development root and writes only its `feishin-rust-dev-p02/profiles-v1.json` child. It rejects symlink components and parent traversal; Windows prefixes are checked only after the root separator forms a valid filesystem path; callers should pass a canonical root on platforms with symlinked temporary directories. The root is trusted, single-owner application data; these path checks do not promise resistance to a hostile concurrent directory replacement. No path is inferred from Electron settings. Run native operations on a bounded filesystem worker, never the UI/async executor. This increment provides the blocking worker boundary, not its production executor integration.

A same-directory temporary file is flushed and synced before atomic replacement; Unix also syncs the directory. Errors after replacement may mean the new value is visible with uncertain durability and are reported. Cross-process writers and power-loss certification on every filesystem/OS are outside this increment. Native tests check replacement/reopen, unchanged original fixture, ignored interrupted temporary data and schema preservation.

The browser adapter replaces one origin-scoped localStorage value under `feishin-rust:dev:p02:profiles:v1`. One-key replacement avoids partial multi-key category writes. Quota/security/disabled storage failures remain errors. The 256 KiB UTF-8 document bound limits serialization and parsing; localStorage retrieval itself necessarily allocates the browser-provided string. Multiple-tab last-writer coordination and larger async IndexedDB stores require follow-up before application integration.

## Alternatives and consequences

SQLite/IndexedDB provide transactions and scale better for queue/cache data but add unnecessary machinery for this bounded profile schema. A shared key with the original app would violate isolation. Multiple split preference keys would need a transaction strategy; the source split-key writer ambiguity remains unmodified and will be characterized in P02.05.

Reads are side-effect-free. Missing fields use documented defaults. Invalid profile records are rejected individually; duplicate IDs keep the first valid profile; an orphan selected ID is cleared. Invalid preference fields default independently with typed recovery diagnostics. Invalid JSON, invalid envelopes and unsupported schema versions fail explicitly and are protected from overwrite by repository saves. Unknown envelope/preferences fields are rejected rather than silently erased. A valid partial-recovery result may be explicitly saved by the caller; no automatic repair write occurs. Whole-document recovery currently requires manually preserving/quarantining the damaged value before starting a new profile; the bounded P02.05 import journal adds one-level target backup/rollback in a separate namespace, without automatically repairing a damaged profile.

Endpoint validation rejects URL userinfo, queries and fragments while allowing intentional HTTP LAN servers and base paths. This is a structural non-secret policy, not a claim to detect arbitrary secrets placed in user text or URL paths. Credentials are excluded by schema and no credential-remembering implementation is selected. Native/browser adapters are not connected to a shell yet.

See [P02 implementation and checks](../p02/README.md) and [migration evidence](../migration/p02-storage.csv). This ADR does not establish full P02 completion or credential/import compatibility.


## Bounded P02.05 continuation

Use explicit copied-input bytes and a read-only partial import preview. Accept only the documented source versions/shapes and project known non-secret preferences, column arrays, Auto DJ settings, server descriptors and queue identity/resume data. Keep column arrays whole, including empty arrays. Preserve duplicate song occurrences and resolve saved current identity through the source shuffle rules before attaching checked timestamps. Unknown categories and unsupported transformations are reported, never silently claimed migrated. Current source exports and synthetic historical fixtures have separate provenance; a real historical-profile corpus is still missing.

Persist the same validated candidate that was previewed in a separate schema-v1 import workspace, alongside one previous target snapshot and a checked revision in one atomic value. Back up target projections rather than original credential-bearing source bytes. A prepared import or rollback is bound to its exact baseline and rejected after an intervening edit. Equivalent freshly prepared imports make no writes. The journal supports one serialized owner, not concurrent multi-process/tab transactions. Production adoption by the settings/queue state owner remains separate.

Alternatives were overwriting the P02.04 profile store, copying full credential-bearing source exports into its non-secret backup, or writing separate current/backup keys without a transaction. The separate single-value journal preserves isolation and makes interruption behavior testable with the current atomic adapters. It also means imported queue/settings data is staged and durable rather than active in the P01 shells. Automatic full settings upgrades, complete queue metadata, runtime hydration/seek restoration and P08 UI mapping are not delivered here.

See the [supported import matrix](../p02/imports.md), [apply/rollback contract](../p02/import-journal.md) and [migration map](../migration/p02-imports.csv). P02.05 remains bounded rather than complete; P02.06 secret remembering and P02.07 cache lifecycle remain explicit follow-ups.

Corrupt-queue index safety: the pinned source filters missing song-map records in `player.store.ts:1101-1119` before `getCurrentSong` indexes the resulting order (`982-994`). Import projection also validates fields and deduplicates occurrence IDs, so its retained order can differ further. If recovery removes or deduplicates a default occurrence, the target rejects current selection and timestamp rather than reinterpreting the saved index. Valid occurrences and priority survive with fixed diagnostics. This is an explicit stricter corrupt-state rule, not a claim of source parity or an upstream bug. The missing-prefix regression covers disabled, album and empty-track shuffle; browser execution separately exercises the missing-prefix case.

## Retained historical transforms

The P02.05 continuation accepts explicit settings versions 0-34 for the retained schema. Early-return, reset and transform paths use each selected category's effective source version, including mixed copies. Outside reset paths, missing whole categories remain unchanged with legacy default deferral reported; the importer does not simulate full source hydration. Valid arrays use the applicable path on a copy before whole-array replacement: early/current arrays can remain empty, versions 12-28 can receive disabled additions, and reset versions remove the imported override collection as described below. Omitted categories/transforms, complete UI defaults and production adoption remain open.

Controlled replay of the exact pinned source confirms two boundary observations: the <=14 column branch addresses lowercase legacy fullscreen/sidequeue keys, and it unconditionally duplicates an already-present bitDepth column. Preserve the source key distinction and report unsupported aliases. Keep an existing target column ID/configuration rather than appending a duplicate, so the validated schema and reimport remain stable. Regression fixtures retain both original output and the intentional target difference. These observations do not establish an active historical UI defect. See [source evidence and behavior](../p02/settings-history.md).

## Early and reset-version continuation

Explicit settings versions 0-34 are supported for the retained schema. Follow the original control flow: 0-9 return before later transforms; 10/11 discard settings; 12 onward reach retained transforms. Supplied early Auto DJ objects fill missing fields through the existing default merge but do not normalize existing aliases. The target rejects invalid current enums with a partial diagnostic. Whole missing categories remain protected under the partial-overlay contract.

For a valid full reset copy, reset only retained settings fields: two preferences, imported column override entries and Auto DJ defaults. Preserve profiles/selected server and queue/current/position. An authoritative reset dominates weaker split copies; supplemental selected reset categories affect only themselves. The preview reports SettingsReset and the existing single-value journal applies that exact projection with a previous target backup. No live/source profile is mutated or active shell state reset.

The source v10 path needs general.sidebarItems.push before returning an empty state. Require its valid structural context; malformed copies do not produce reset previews. The source v11 path can discard null state/General, but the target rejects malformed typed envelopes to prevent accidental resets. Original outputs and the intentional stricter validation are saved in the [early/reset evidence](../p02/early-settings.md). Complete UI defaults and production adoption remain open rather than inferred from retained-field resets.

## Active durable-state continuation

Accept `state::StateRepository` as the single mutable owner of the active retained durable schema, staged journal and read-only legacy profile input. Store current state, one backup and monotone revision in one new atomic value (`state-v1.json`/`feishin-rust:dev:p02:state:v1`). Do not mirror active changes into the older profile or import value. Before activation, synthesize revision zero from the validated v1 profile and expose its recovery diagnostics; after activation, the active value alone is authoritative. First activation backs up that synthesized state, preserving undo compatibility with v1 inputs without changing those inputs.

Adoption explicitly replaces the complete retained projection with the reviewed stage; it does not silently overlay an import built against a different baseline. Immutable before/after snapshots and exact target/stage/initial-profile byte guards make that replacement reviewable and reject intervening edits. Local saves and rollback use the same active envelope. A successfully returned snapshot follows a successful replacement; uncertain durability requires reload/reconciliation. Existing bounds, non-secret validators and one serialized worker limitation apply. This implements a repository boundary, not production shell hydration, actor scheduling or queue/playback restoration.

Alternatives were two independent writes to profile/journal (no atomic rollback), treating staging as active implicitly (no adoption review), or adding SQLite/IndexedDB transactions now (unneeded for the existing bounded retained schema). The selected third namespace requires a future application composition to choose this owner instead of continuing to write the legacy profile. The source auth merge (`auth.store.ts:114`), settings migration (`settings.store.ts:2442`) and separate player/queue writes (`utils.ts:119-143`) establish source persistence behavior, not source atomicity across these categories. The unified envelope and explicit replacement policy are target decisions. See [contract and compatibility](../p02/state-adoption.md), [migration evidence](../migration/p02-state.csv) and [checks](../p02/state-adoption-verification.md).

## Storage worker continuation

Accept a typed portable `session::Session` and a native `NativeWorker` inside the existing storage crate. Session owns repository handles and retains one prepared stage/active operation. Opaque generation-scoped review tokens supersede on successful preparation and are consumed on apply attempts, including failures. The wrapper does not reconstruct a candidate at apply time or silently retry a mutation. Byte admission precedes parsing; the worker thread performs native opening, parsing, projection and storage operations. Completed-but-unread replies count toward the 1-8 outstanding admission bound. A Send factory can construct non-Send stores on that thread; portable storage/session boundaries require no Send bound.

The native wrapper uses a dedicated thread and nonblocking submit/poll instead of adding a general async runtime or blocking the UI with filesystem work. Explicit shutdown closes admission, rejects queued work and permits an active operation to finish; joining is conditional on observed thread completion. No thread API can forcibly interrupt a blocked filesystem call. Deadline/cancellation checks are latest-start gates and cannot change the outcome of a write already dispatched. Cross-process/tab CAS remains unimplemented.

Browser localStorage stays a local synchronous dispatcher path, verified separately from native threading. It is unavailable in Web Workers. IndexedDB/message-worker composition and browser frame-latency evidence remain later work. The alternative of claiming a universal background worker over Window-only storage was rejected; moving to a new browser database during this bounded task would require a separate compatibility decision. Shell/UI integration remains open, and none of this establishes P05 playback ownership or full P02.07 cancellation. See [protocol and lifecycle](../p02/state-worker.md) and [checks](../p02/state-worker-verification.md).
