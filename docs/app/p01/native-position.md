# P01.05 native position readiness and seek observation

The managed mpv candidate now exposes `probe_position(timeout) -> Result<Option<f64>, Error>`. It returns `None` only for the exact correlated `property unavailable` response. This is normal while idle/loading and leaves the current engine usable. A successful position must be finite and non-negative. Invalid success data, other correlated rejection, process/transport failure and in-flight query timeout invalidate the transport; partial replies cannot be reused as if the next command succeeded. `position()` retains a strict numeric result, returning the typed `PropertyUnavailable` error for absence without poisoning the process.

Each query uses the smaller of the caller's remaining budget and the existing three-second command maximum, including writes, partial reads and unrelated/event replies. A zero budget returns before issuing a request and preserves engine state. These remain blocking native worker/CLI APIs; the UI, portable model and WASM code do not call them.

The external native IPC test previously slept 250 ms after load and read the position immediately after a seek acknowledgement. Neither establishes readiness or arrival. It now pauses before loading, checks the real idle/unavailable response, waits for a position near zero, issues the seek and waits for the paused position within 100 ms of one second, under one three-second budget for each wait. The wait helper is test-only. It does not implement a production playback state owner, general seeking policy or device/timestamp acknowledgement. The public `seek()` still reports command acceptance.

The [five default Unix regressions](../../../tests/native-spike/position.rs) use a [controlled IPC peer](../../../tests/native-spike/fake_mpv.py): unavailable values followed by readiness, successful seek acknowledgement followed by several stale positions, permanent absence/mismatch, short-budget partial replies, negative/null/string success data, unrelated rejection and zero/oversized caller budgets. Query-count-driven stale replies make the acknowledgement/arrival difference deterministic. The existing [Windows named-pipe peer/tests](../../../tests/native-spike/windows_pipe.rs) add unavailable-versus-rejected/invalid values and a normal correlated numeric position. Windows code is cross-compiled locally; its new runtime assertions await hosted Windows execution. No real Windows mpv/device claim is made.

The crossfade readiness loop uses the same query API with its remaining four-second budget; it no longer retries every generic rejection or starts a fresh three-second query after its own budget has nearly expired. The optional live calibration, three-curve crossfade and 19-case transition captures are rerun against the changed transport. Use the isolated setup and commands in [crossfade](crossfade.md) and [native transitions](native-transitions.md); no host audio source or physical output is used. Default CI still captures no audio and the external wrapper still selects exactly its five ignored probes.
