# P01.04 browser element seek lifecycle

The feasibility adapter now observes the audio element's `seeking` event and shares one cancellable request/deadline with Media Session callback seeks. A new observed target replaces the previous request; the callback's own matching event keeps the existing deadline. `seeked` must report a finite position within 250 ms of the latest target. Missing completion reaches the existing eight-second browser timer, pauses playback and requires the visible Load/Play action to reload. Source replacement, errors and shutdown cancel the shared request.

Play requests also show a starting status immediately, preventing a stale success message from describing an unresolved replacement. A held play-promise regression checks that status before the current request settles.

The event reports the element's current target; it does not identify the input device or carry an application request ID. This is a single-element prototype policy for the latest observed target, not a production queue/engine coordinator. No-op native seeks need no event; finite-duration streams remain the tested scope. A native control rejection that emits no event cannot be observed by this listener. Browser suspension can delay the event loop and timers, so the deadline is not a physical latency guarantee.

The optional [browser scenario](../../../tests/browser/p01-browser.cjs) adds [element-seek regressions](../../../tests/browser/native-seek-lifecycle.cjs) through the real WASM adapter. Direct `audio.currentTime` assignment exercises the browser's actual element seek-event path; it does not click a platform's built-in scrubber or prove physical input/accessibility. The tests withhold a real completion event to provoke the deadline, and separately override the reported position at a real completion to check mismatch failure. The existing callback fault injection holds one request without a seek event. No seek-completion event is fabricated. All overrides/listeners are scoped to the disposable fixture and restored.
