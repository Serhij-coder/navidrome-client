# Reviewed import apply, backup and rollback

`JournalRepository` complements the [copied-input projector](imports.md). It persists a reviewed, bounded non-secret target projection, not the original source bytes. It is not yet adopted by a shell or the production queue/settings owner.

The caller explicitly supplies copied JSON bytes, calls `prepare`, reviews the immutable candidate and typed report, then calls `apply` with that same prepared object. The repository prepares against its current imported state or an empty state. Projection of selected categories preserves unaffected target fields. `prepare` performs no writes and checks that both the candidate and its one-level backup fit the 256 KiB journal limit before presenting a result.

Native storage uses `NativeStore::open_imports(canonical_development_root)` and writes only `feishin-rust-dev-p02/imports-v1.json`. Browser storage uses `BrowserStore::open_imports()` and `feishin-rust:dev:p02:imports:v1`. The earlier non-secret profile store and upstream-named keys are separate. No Electron profile discovery, source file write, credential import, live-profile migration or implicit application of imported settings occurs.

The schema-v1 envelope has a monotonically increasing revision, current target data and one previous target snapshot. A single atomic value contains all three. Native replacement uses the existing same-directory temporary-file/sync/replace boundary; browser replacement uses one localStorage value. A failed replacement that preserves the old bytes leaves both current and backup unchanged. If an I/O error occurs after a visible replacement, the caller must reload and reconcile; the error is never reported as success or automatically retried.

`prepare_rollback` exposes the backup without writing. `rollback` restores that exact reviewed data with a new revision and retains the replaced current value as the next backup. This is one-level undo/redo, not a history archive. The first import can be rolled back to an empty imported workspace. The backup contains validated target data only; it deliberately does not duplicate source credentials or unsupported raw settings.

Both prepared operations retain the exact baseline target bytes. An intervening change makes the operation return `Conflict` before writing. A newly prepared equivalent import is idempotent and does not increment the revision, replace the backup or write. Applying a consumed baseline again returns `Conflict`. These checks support one serialized owner and detect intervening edits; they are not a cross-process/tab compare-and-swap or writer lock. Concurrent external writers remain unsupported.

Load validates schema, envelope fields, revision ordering, current data and backup data. Corrupt JSON, invalid backup/current state, unsupported future schemas, oversized data and exhausted revisions fail explicitly and are protected from mutation. Atomic replacement protects interrupted writes, while read-only failure preserves a damaged journal for external recovery. This does not promise recovery from arbitrary whole-file bit rot when both snapshots occupy the same damaged value, or certify power-loss behavior on every filesystem.

All projection and native repository methods are synchronous bounded worker APIs. Production composition must run large import parsing/validation and native I/O off the UI/async executor. The browser runtime tests use a small synthetic input; full worker/message composition and large-export responsiveness remain unimplemented.

The [journal integration target](../../../tests/storage/journal.rs) checks immutable preview/apply, idempotence, stale operations, rollback/redo/reopen, failure/retry, uncertain durability, corrupt/future/invalid backups, revision exhaustion, capacity including backup, namespace isolation and interrupted temporary data. The [browser fixture](../../../tests/browser/p02-imports.cjs) checks real origin storage/reload, rollback/redo, stale rejection, namespace isolation, injected quota failure and future-schema protection in fresh browser contexts. It uses the test-only WASM example and never opens a user export.
